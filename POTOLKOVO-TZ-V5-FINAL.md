## 0. Главная поправка к предыдущим документам — прочитать первым

**Прод-домен на момент проверки этого документа (10.09.2026, ~12:44 UTC) отвечает `HTTP/2 200`, а не `503`.**

```
$ curl -sI https://potolkovo-msk.ru/
HTTP/2 200
x-nextjs-cache: HIT
x-nextjs-prerender: 1
x-powered-by: Next.js
...
$ curl -o /dev/null -s -w "%{http_code}\n" https://potolkovo-msk.ru/uslugi
200
$ curl -o /dev/null -s -w "%{http_code}\n" https://potolkovo-msk.ru/api/health
404   # эндпоинта /api/health в этом репозитории нет вовсе — 404, не 503
```

Документ B (раздел 0 и 5) сделал вывод «продакшен-сайт сейчас недоступен» и поставил восстановление домена задачей номер один. На момент этой проверки вывод **не подтверждается**: главная и `/uslugi` отдают `200` с корректной серверной отрисовкой (`x-nextjs-prerender`, ETag, реальный HTML 147 КБ). Это либо (а) инцидент был кратковременным и уже устранён владельцем/платформой без участия агента, либо (б) наблюдение аудита B само было точечным сбоем инфраструктуры Amvera в момент его проверки. Ни то, ни другое нельзя утверждать с уверенностью — **у нас нет доступа к логам Amvera**, только к двум точечным HTTP-снимкам в разные моменты времени.

**Практический вывод для агента, а не философский:** факт, что сайт **дважды** за примерно один день менял состояние между «полностью недоступен» и «полностью доступен» без единого коммита в код — сам по себе находка более серьёзная, чем любая отдельная 503. Это означает нестабильность деплоя/раннера на PaaS, отсутствие health-check/readiness-эндпоинта, который мог бы объяснить причину, и отсутствие любого внешнего мониторинга, который зафиксировал бы, когда именно и почему это произошло. Поэтому:

- Задача «расследовать причину прошлого 503» **понижена** из аварийной P0 «чинить прямо сейчас» до P0 «добавить наблюдаемость, чтобы такое не повторялось незамеченным» — см. **PT‑001**.
- Все находки, которые не зависят от доступности домена (сохранность заявок, целостность расчёта, безопасность зависимостей), **сохраняют исходный приоритет** — они подтверждены чтением кода на HEAD, а не поведением одного HTTP-запроса.
- Агент, начинающий работу, обязан **сам** заново выполнить `curl -I https://potolkovo-msk.ru/` перед стартом и зафиксировать текущий статус в первом отчёте — не полагаться ни на «503» из документа B, ни на «200» из этого документа: оба являются снимками на момент времени.

## 2. Неизменные правила (обязательны для всех задач)

Эти правила действуют для агента на протяжении всей работы, независимо от фазы:

1. **Ветвление.** Работать в `quizv2ver1-fix/<фаза>` (например, `quizv2ver1-fix/p0`), не в `main` и не напрямую в `quizv2ver1`. Один коммит/PR = одна задача `PT‑0xx`. Сообщение коммита включает ID задачи и краткую причину.
2. **Цены — только в одном месте.** Единственный источник цен и процентов — `content/pricing.ts` (см. Приложение A, значения перепроверены по текущему коду). Любое числовое расхождение между `pricing.ts` и текстами/JSON‑LD — баг. Менять цены нельзя нигде больше, включая тексты услуг и hero.
3. **Не удалять и не переименовывать публичные URL, якоря секций (`hero`, `proof`, `price`, `trust`, `promise`, `action`), JSON‑LD, `sitemap.xml`, `robots.txt`** без замены с 301-редиректом и обновлением всех внутренних ссылок.
4. **`useEffect` не используется для синхронизации состояний.** Разрешённые случаи — навигация, фокус, загрузка данных. В `components/calculator-modal/**` есть страж `scripts/check-effect-setstate.mjs` (входит в `prebuild`) — он обязан оставаться зелёным; новые нарушения не добавлять.
5. **Никаких выдуманных фактов.** Реквизиты, адреса, отзывы, рейтинги, «звёзды», гарантии сроков, статистика конверсии — либо подтверждены владельцем/данными, либо не публикуются. Формулировки без измерения — как гипотеза, а не факт (`A-F16`, `T-335`).
6. **`npm audit fix --force` запрещён вслепую.** Каждое high/critical advisory разбирается вручную: применимо ли оно к реальному пути выполнения (серверный self-hosted Node на Amvera, не Vercel edge; `next.config.ts` держит `images: { unoptimized: true }` — часть находок про Image Optimizer/AVIF неприменима, пока это так, но апгрейд всё равно обязателен).
7. **Тесты не подделываются.** Запрещено: удалять тест ради зелёного CI, добавлять `skip` без письменной причины и владельца, использовать production payload (реальный телефон/адрес/платёж) в тестах, отправлять реальные уведомления в Telegram/почту из автотестов — только фейковый provider/мок HTTP-сервер.
8. **Флаги для крупных поведенческих изменений.** По аналогии с `NEXT_PUBLIC_CALC_QUIZ_V2`, `LEAD_API_ENABLED`, `TELEGRAM_LEADS_ENABLED` — новая логика приёма/обработки заявок должна включаться отдельным флагом с безопасным дефолтом, чтобы можно было откатить без деплоя нового кода.
9. **Отчёт по каждой задаче обязателен** и содержит: что сделано и почему (со ссылкой на исходную находку `A-xx`/`B-Fxx`/`PT-xx`), изменённые файлы, добавленный/изменённый regression-тест, точный вывод каждой прогнанной команды (не «тесты прошли», а вставленный лог), список известных ограничений, инструкция по откату.
10. **Если у агента нет доступа к чему-то (прод, БД, Метрика, CRM, реальное устройство)** — он обязан явно написать «проверка не выполнена, доступ отсутствует» и дать владельцу пошаговую команду/инструкцию для самостоятельной проверки. Подделывать результат недопустимо.

## 3. Архитектурные инварианты (обязательны к соблюдению при любой правке ядра)

Эти инварианты синтезированы из документа A (раздел 03) и подтверждены текущим кодом `lib/calculator/*`, `content/pricing.ts`, `app/api/lead/route.ts`.

### 3.1. EntryContext (контекст входа в квиз)
Тип: `{ pagePath, serviceSlug, placement, entryMode, intent, presetOrigin, preset: ServiceCalculatorPreset }`. `presetOrigin` различает `default` (обычный вход с главной/хедера без данных услуги), `page` (пришли со страницы услуги/кейса — есть частичный пресет) и `explicit` (полный пресет конкретного кейса, например «18 м² / 19 м профиля / 10 м трека»). Источник входа не должен распознаваться подстрокой произвольной строки `source` — использовать типизированный union.

### 3.2. Draft (черновик расчёта в браузере)
Поля: `version, updatedAt, scenario, scope, rooms, lighting (корзина света целиком, не только комнаты), intent, pricingVersion`. При чтении — валидация схемой; известная старая версия — миграция; неизвестная версия — безопасный отказ с явным выбором «начать новый расчёт», не молчаливая перезапись и не падение UI. **Черновик не перезаписывается**, пока пользователь явно не выбрал «Продолжить» или «Новый расчёт» при наличии конфликта между сохранённым состоянием и новым `entryPreset`. Телефон и адрес в `localStorage`/`sessionStorage` не сохраняются.

### 3.3. Расчёт (pricing)
Единый чистый модуль без побочных эффектов, используемый и клиентом (мгновенный предпросмотр), и сервером (авторитетный пересчёт). Источник истины на сервере — нормализованные входные параметры (SKU, количества, метраж, тип сценария) плюс серверная копия `content/pricing.ts` и каталога света, а не значения, присланные клиентом. Инвариант суммы (подтверждён комментарием в README и кодом): `grand = ceilingApplied + extraInstallRub + lightingEffective`. Минимальный заказ (`18 000 ₽`) применяется один раз к согласованной области. Досчёт монтажа считается **только вверх**: если в корзине света меньше корпусов, чем заложено в потолке, ничего не вычитается. Скидки на свет (`-25%` с потолком, `-10%` только свет) не складываются друг с другом — подтвердить у владельца, что правило именно «либо/либо», а не аддитивное, прежде чем переносить на сервер.

### 3.4. `POST /api/lead` — целевой конвейер
`Ограничение размера запроса → JSON parsing → honeypot/anti-abuse → строгая zod-схема обязательных полей + мягкая нормализация optional attribution → серверный пересчёт снапшота → транзакция (лид + outbox-задания на доставку) → 201 saved/queued`. **Сетевая доставка в Telegram/Web3Forms не должна происходить синхронно внутри этого запроса** (текущий код именно так и делает — см. PT‑003) — доступность записи важнее синхронного уведомления, но состояние ответа клиенту должно быть честным («сохранено», а не «доставлено мастеру»).

### 3.5. Идемпотентность
Клиентский `requestId` (UUID) генерируется один раз на попытку отправки и живёт до успеха. Сервер дополнительно хранит хеш канонического payload. `UNIQUE(requestId)`. Повтор того же `requestId` с тем же хешем — возвращает прежний результат без побочных эффектов; тот же `requestId` с другим хешем (что не должно случаться при корректном клиенте, но должно быть безопасно на сервере) — `409`. Один и тот же телефон с изменившимся составом заказа в течение окна дедупа — **новая запись**, а не переиспользование старой (это прямое расхождение с текущим поведением `findRecentByPhone`, см. PT‑009).

### 3.6. Outbox для доставки
Отдельная сущность заданий на доставку со статусами `pending → processing → sent | failed → dead`; `attempts`, `nextAttemptAt`, `leaseUntil`, `lastErrorCode`, `providerMessageId`, `sentAt`. Захват задания — атомарная операция (`SELECT … FOR UPDATE SKIP LOCKED` или эквивалент), чтобы два параллельных запуска ретрая не отправили одно сообщение дважды в обычном случае. Таймаут провайдера + экспоненциальный backoff с джиттером + ограничение попыток + видимый dead-letter. **At-least-once, не exactly-once** — прямо документировать это ограничение, не обещать невозможного.

### 3.7. Согласие (consent)
Версия неизменяемого текста политики, серверное время получения согласия, цель обработки и форма, из которой оно получено — хранятся в БД вместе с лидом (сейчас не хранятся вовсе, см. PT‑015). Rescue-форма не может отправлять `consent: true` как константу без показа пользователю текста согласия (сейчас именно так и происходит, см. PT‑004).

### 3.8. Совместимость API при миграциях
`expand → migrate → switch → contract`. Старые версии сохранённого драфта либо мигрируются, либо получают понятную версионную ошибку с предложением начать заново — никогда не должны валиться в необработанное исключение. Миграции БД — идемпотентны, проверяются на обезличенной копии, предусматривают откат кода без потери уже накопленных данных.

## 4. Консолидированный реестр задач

Легенда приоритета: **P0** — риск потери/ложного приёма заявки, применимая уязвимость или полная непредсказуемость релиза; **P1** — воспроизводимый разрыв пользовательского/коммерческого сценария; **P2** — качество, измеримость, технический долг с известной ценой; **P3** — гипотеза роста, требует baseline и осторожного A/B, не может быть «доказанным улучшением» без данных.

Каждая задача ссылается на исходные находки обоих документов (`A-xx`/`A-Fxx` — документ A, `B-Fxx`/`T-3xx` — документ B) — полная таблица соответствий в Приложении D.

### P0 — не терять деньги, данные и не запускать сайт со сломанным ядром

#### PT‑001 · Наблюдаемость прод-окружения: health/readiness + рантайм-факты
**Источники:** новая находка этого документа (раздел 0) + `T‑301` (переоценено), пересекается с `A‑01`.
**Проблема.** В репозитории нет `/api/health` (подтверждено: `curl .../api/health` → `404`, самого файла нет в дереве `app/api/`). Из-за этого невозможно объективно отличить «приложение работает, но лиды падают в память» от «приложение вообще не поднялось», и невозможно настроить PaaS/внешний мониторинг на осмысленную проверку готовности. Наблюдавшееся расхождение 503↔200 за один день не имеет диагностического следа.
**Решение.** Добавить `GET /api/health`, отвечающий быстро (без похода в БД дольше 1.5–2 c с собственным таймаутом) и без утечки конфигурации: `{ ok: true, storage: "db"|"memory", deliveryChannels: { telegram: boolean, web3forms: boolean }, buildSha, uptimeSec }`. Настроить в Amvera (или у любого внешнего синтетического монитора, например UptimeRobot/healthchecks.io — не требует доступа к панели Amvera, можно подключить снаружи) периодический опрос `/`, `/uslugi`, `/api/health` с алертом владельцу. Написать короткий runbook «сайт не отвечает — что проверить» (переменные окружения, `containerPort`, лог последнего деплоя, `prebuild`-скрипты).
**Приёмка.** `curl https://potolkovo-msk.ru/api/health` → `200` с корректным `storage`. Внешний монитор настроен и присылает алерт при первой же проверке (тест — временно остановить сервис, если у владельца есть доступ, либо отправить заведомо некорректный запрос и убедиться в детектировании через сам мониторинг). Runbook в README.

#### PT‑002 · Явный отказ вместо тихого отката на in-memory хранилище в проде
**Источники:** `A‑01` · `B‑F102` · `T‑303`. Код подтверждён построчно: `lib/lead/store.ts`, функция `getLeadStore()` — при пустом `DATABASE_URL` пишет `console.warn` и молча возвращает `InMemoryLeadStore`, включая `NODE_ENV=production`.
**Проблема.** InMemoryLeadStore теряет все заявки при перезапуске процесса/холодном старте, ломает дедуп, серверный rate-limit и поиск по коду — но HTTP-ответ клиенту при этом полностью успешный (`201`), пользователь не узнает, что его заявка не переживёт рестарт.
**Решение.** В `getLeadStore()` — если `process.env.NODE_ENV === "production"` и `DATABASE_URL` пуст, не тихий warn, а: (а) либо `throw` при инициализации модуля (сервис не поднимется, что видно в логах платформы и сработает `PT‑001`), либо (б) осознанный «режим деградации» — `/api/lead` отвечает `503 { ok:false, error:"storage_unavailable" }`, а не создаёт видимость успеха. Второй вариант предпочтительнее первого, если владелец не готов к полной остановке сайта при проблеме с БД — но выбор конкретного поведения нужно явно согласовать, не решать в одиночку молча. Разработка/preview без флага — поведение не менять.
**Приёмка.** `NODE_ENV=production npm run start` без `DATABASE_URL` — либо не стартует с понятной ошибкой, либо `/api/lead` детерминированно отвечает `503` вместо `201`. С валидным `DATABASE_URL` поведение не меняется.

#### PT‑003 · Атомарная запись лида и очереди доставки; доставка — не в теле запроса
**Источники:** `A‑02`, `A‑08`, `A‑23` · `B‑F112` · `T‑309`, `T‑315`. Подтверждено чтением `app/api/lead/route.ts` и `lib/lead/store-pg.ts`: `createLead()` выполняется, затем `Promise.all([deliverToTelegram, deliverToWeb3Forms])` — то есть HTTP-ответ клиенту ждёт двух внешних сетевых вызовов, а `recordDelivery()` для каждого канала пишется отдельным вызовом БД **после** попытки доставки. Атомарной транзакции «лид + задания на доставку» нет; отдельного `outbox` до попытки отправки — нет.
**Проблема.** (1) Остановка процесса между `createLead` и `recordDelivery` оставляет лид без единой записи о статусе доставки — задание не запланировано, крон `retry` его не увидит (он смотрит на `lead_deliveries.status = 'failed'`, а строки может не быть вовсе). (2) Клиент физически ждёт ответа от Telegram/Web3Forms в одном запросе — при их деградации форма «зависает» на клиенте вместо мгновенного «сохранено». (3) Нет атомарного захвата задания — прямой параллельный `retry` потенциально обработает одну и ту же зависшую доставку дважды.
**Решение.** Ввести таблицу/сущность outbox-заданий, создаваемую **в одной транзакции** с `leads` со статусом `pending` сразу для обоих каналов. Сам HTTP-обработчик `/api/lead` **не должен** дожидаться доставки — либо запускает её асинхронно «после ответа» (`waitUntil`-подобный паттерн или fire-and-forget с гарантированным подхватом кроном при неудаче), либо всегда возвращает успех сразу после commit транзакции, а доставка целиком идёт через уже существующий `/api/lead/retry`, вызываемый чаще (например, раз в минуту) для новых `pending`-заданий, а не только для `failed`. Добавить уникальный индекс `(lead_id, channel)` и атомарный `claim` (`FOR UPDATE SKIP LOCKED` или `UPDATE ... WHERE status='pending' AND (lease_until IS NULL OR lease_until < now()) RETURNING`).
**Приёмка.** Симуляция обрыва процесса сразу после ответа `201` не оставляет «повисших» лидов без задания на доставку. Два параллельных вызова `retry` не отправляют один и тот же канал дважды (проверить логированием `providerMessageId`/`attempts`). Клиентский `POST /api/lead` отвечает за миллисекунды, не дожидаясь ответа Telegram/Web3Forms.

#### PT‑004 · Rescue-заявка: полный снапшот, проверка ответа, реальное согласие
**Источники:** `A‑03` · `T‑307`. Подтверждено дословно в `components/calculator-modal/calculator-modal.tsx`, функция `submitRescueLead`: отправляется только `{ phone, consent: true, source, placement: "rescue", leadKind: "rescue", pagePath, grandTotal }` — без `snapshot`/`totals`/состава комнат/корзины света; `fetch` обёрнут в `try { await fetch(...); markLeadSubmitted(); } catch { /* rescue не должен мешать закрытию модалки */ }` — то есть `markLeadSubmitted()` вызывается **даже если сервер ответил `422/429/500`**, потому что `fetch` не бросает исключение на HTTP-ошибках, а `response.ok`/`response.json()` вообще не проверяются. `consent: true` — захардкоженная константа, пользователь не видел текста согласия.
**Решение.** Использовать общий submit-сервис с тем же контрактом, что и основная форма: отправлять `LeadSnapshotV2` целиком (все комнаты + корзина света, даже в укороченном rescue-сценарии), проверять `response.ok && body.ok` перед вызовом `markLeadSubmitted()`, при ошибке показывать состояние retry, а не молчаливый «успех». Добавить видимый чекбокс/текст согласия перед отправкой rescue-заявки (см. PT‑015).
**Приёмка.** Мок `422/429/500`/сетевая ошибка → UI не показывает успех и не считает `lead_submit` отправленным. При `201` в записанном лиде присутствуют все позиции расчёта, а не только сумма. Без явного согласия rescue-запрос не уходит.

Отдельно зафиксировать в отчёте PR: какие из перечисленных CVE применимы к текущей конфигурации (self-hosted Node — да, unoptimized images — снижает риск AVIF, Linux — снимает Windows RCE), какие закрыты самим фактом апгрейда. Прогнать полный gate (раздел 6) после обновления.
**Приёмка.** `npm ls next react react-dom` показывает версии без открытых high/critical advisory в `npm audit --omit=dev` (документировать оставшиеся исключения с обоснованием неприменимости и владельцем). Полный пайплайн (раздел 6) зелёный после апгрейда.

#### PT‑007 · Восстановление черновика не должно происходить без согласия пользователя

#### PT‑009 · Идемпотентность вместо дедупа по телефону
**Источники:** `A‑07` · `T‑308`. Подтверждено: `findRecentByPhone(phone, DEDUPE_WINDOW_MS=10 мин)` в `store-pg.ts`/`store.ts` возвращает **любую** предыдущую заявку с тем же телефоном за 10 минут, независимо от состава заказа — то есть если человек сначала отправил rescue-заявку (только сумма), а через минуту досчитал полную комплектацию и отправил снова, вторая отправка молча вернёт `{ ok:true, deduped:true }` с кодом **первой**, неполной заявки, и новая (полная) информация нигде не сохранится.
**Решение.** Ввести клиентский `requestId` (UUID на одну попытку отправки) + серверный хеш нормализованного payload (раздел 3.5). `UNIQUE(requestId)` в схеме БД. Повтор с тем же `requestId` и тем же хешем — старый результат без побочных эффектов. Тот же телефон с другим составом — новая запись всегда, дедуп по телефону как эвристика анти-спама может остаться отдельно от идемпотентности, но не должен подменять/поглощать содержательно другую заявку.
**Приёмка.** Двойной клик «Отправить» с одинаковым payload создаёт одну запись и одно задание доставки. Rescue → полная заявка с тем же телефоном в течение 10 минут создаёт **вторую**, полную запись, не возвращает код rescue-заявки.

#### PT‑010 · Серверный пересчёт цены — сервер не доверяет сумме от клиента
**Источники:** `A‑08`(MD, `F-10`), `A‑10` · `T‑311`. Подтверждено: `LeadPayloadSchema` (`lib/lead/schema.ts`) принимает `snapshot`/`totals`/`grandTotal` как есть; `grandTotal` в `route.ts` берётся `payload.snapshot?.totals.grand ?? payload.totals?.grand ?? payload.grandTotal ?? 0` — без пересчёта по каталогу и `content/pricing.ts` на сервере. Неотрицательное число само по себе не подтверждает, что цена/скидка/SKU допустимы.
**Решение.** Сервер извлекает из присланного снапшота только **нормализованные параметры** (тип потолка, площадь, метраж профиля/трека/карниза, SKU и количества света) и пересчитывает `grand` тем же чистым модулем `pricing`, что использует клиент, по серверной копии `content/pricing.ts` и текущего индекса каталога. Присланная клиентом сумма используется только для сверки/алерта при расхождении (например, лог с разницей > 1% — не блокирует лида, но подсвечивает возможную рассинхронизацию версий прайса на клиенте, а не попытку подмены).
**Приёмка.** Искусственно заниженный `grandTotal`/`priceRub`/`discountPercentApplied` в теле запроса от клиента не проходит в БД как авторитетное значение — записывается пересчитанное сервером число. Неизвестный SKU и дробное количество штучного товара отклоняются валидацией.

#### PT‑015 · Алерт при систематических сбоях доставки

## 6. Порядок работ, фазы и обязательные gate-проверки

**Порядок:** Фаза 0 (наблюдаемость и юридический гейт: PT‑001, PT‑002, PT‑006) → Фаза 1 (сохранность заявки: PT‑003, PT‑004, PT‑009) → Фаза 2 (целостность расчёта и контекста: PT‑007, PT‑008, PT‑010) → Фаза 3 (безопасность зависимостей: PT‑005, может выполняться параллельно с Фазой 0 как отдельный независимый PR) → Фаза 4 (предсказуемость UX: PT‑011…PT‑023) → Фаза 5 (тестовая защита и техдолг: PT‑018…PT‑021) → Фаза 6 (измерение: PT‑024…PT‑030) → Фаза 7 (гипотезы роста: PT‑031…PT‑037, только с baseline).

Внутри фазы можно параллелить независимые задачи, но нельзя одновременно менять визуальный слой и ядро расчёта в одном PR. Каждая следующая фаза начинается только после «зелёного» состояния предыдущей.

**Обязательный gate перед переходом к следующей фазе и перед завершением работы:**

```
npm ci
npm run lint                    # 0 errors
npx tsc --noEmit                 # 0 errors
npm run validate:catalog
DATABASE_URL=... npx drizzle-kit push --force   # изолированная тестовая БД
TEST_DATABASE_URL=... npm run test              # vitest, включая ранее падавший test:flow
npm run test:flow
npm run build                    # успешная сборка
npm run check:bundle             # главная ≤ 300 КБ gzip First Load JS
npm run test:e2e                 # Playwright, 0 unexpected failures
npm audit --omit=dev             # 0 необработанных high/critical в production-графе
curl -I https://<стейджинг-или-прод>/        # 200
curl https://<стейджинг-или-прод>/api/health # 200, после PT-001
```

Если любая проверка падает — сначала смотреть лог соответствующей команды, чинить код, не изменять сами проверки ради зелёного статуса (правило 7, раздел 2).

## 7. Что не разрешено ни при каких обстоятельствах

- Удалять тест или снижать порог, чтобы получить зелёный CI.
- Добавлять `skip` без письменной причины, владельца и срока.

- Передавать реальный payload заявки (телефон, адрес) во внешние AI/аналитические сервисы при отладке.
- Запускать реальные тестовые заявки в боевые каналы Telegram/Web3Forms без явного согласования с владельцем канала.

## Итог

Инженерная база проекта (PostgreSQL для лидов, честная самодокументация технического долга в `PHASE-*-REPORT.md`, CI со статическими проверками, тестами и `gitleaks`) подтверждена независимо и этим документом при чтении актуального кода — это сильная сторона, не маркетинговое заявление. Одновременно подтверждены построчно все проверенные P0/P1 находки документов A и B: тихий откат на in-memory хранилище в проде, синхронная доставка внутри запроса без атомарного outbox, потеря снапшота и отсутствие проверки ответа в rescue-заявке, дедуп по телефону вместо идемпотентности, доверие клиентской цене, отставание от патченной версии Next.js, юридический гейт без реального эффекта в CI/деплое. Единственная существенная поправка этого документа к предшественникам — статус домена на момент проверки (`200`, не `503`), которая не отменяет ни одной находки на уровне кода, но меняет первую практическую задачу агента с «чинить сайт» на «сделать так, чтобы падения и восстановления домена больше не оставались незамеченными» (PT‑001). Порядок работы — от P0 к P3, один PR — один проверяемый риск, каждая гипотеза роста проверяется данными, а не мнением.
