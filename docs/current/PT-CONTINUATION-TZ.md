### PT-021 · Доверенный источник IP и защита от переполнения тела запроса

**Статус:** РЕАЛИЗОВАНО В КОДЕ, LOCAL_VERIFIED. Первый `x-forwarded-for` больше не считается адресом клиента; тело читается с лимитом до JSON/Zod. `platform_verified: false` — конфигурация ingress Amvera/Vercel не подтверждена.

**Что изменено.** `lib/lead/client-ip.ts`: адрес берётся с позиции `len - hops` цепочки XFF, хвост отбрасывается, `x-real-ip` — только при объявленных доверенных прокси, валидация через `node:net` `isIP`, нормализация IPv4:port и `[IPv6]:port`. Неподтверждённая цепочка → `unknown` + причина (`chain-too-short`/`invalid-address`/`header-missing`/`no-trusted-proxy`), ключ лимита стабилен. `lib/lead/read-json-body.ts`: `LEAD_MAX_BODY_BYTES = 256 КиБ` считается по фактически прочитанным байтам потоковым `TextDecoder`; `Content-Length` — только ранний выход, при превышении `reader.cancel()`. Ответ `413 payload_too_large` формируется до хранилища, honeypot, лимитера, Zod и доставки. Флаг `LEAD_TRUSTED_PROXY_HOPS` (`intFlag(1, 0, 10)` в `lib/env.ts`): `0` — доверенных прокси нет, XFF и `x-real-ip` игнорируются; нецелое значение попадает в `env.warnings`. Флаг `0` для числа прокси = поведение «все в корзине unknown», откат правки — revert коммита.

**Проверки.** `tests/lead-client-ip.test.ts` (11) и `tests/lead-body-limit.test.ts` (9): поддельный XFF, цепочка из двух прокси, `hops=0`, короткая цепочка, битый адрес, `x-real-ip`, честный/заниженный/отсутствующий `Content-Length`, chunked-переполнение с обрывом чтения, многобайтный UTF-8 разрезанный между чанками, malformed JSON, обычная заявка, `413` без записи в хранилище и без вызова каналов, лимит не обходится сменой XFF. Unit **109 файлов / 1434 passed / 0 failed**, полный E2E **336 passed / 16 skipped / 0 failed** (`--workers=1`, 14.5 мин), `tsc` и eslint по изменённым файлам чисто, build 0, `/` **228.4 КБ gzip**.

**Приоритет исходного плана:** P1. **Связь:** T8-007.

**Источники:** `A‑24`(MD, `F-24`) · `T‑316`. `clientIp()` в `route.ts` берёт первый элемент `x-forwarded-for` без проверки, что заголовок действительно переписывается доверенным прокси/ingress платформы Amvera, а не приходит от клиента как есть. Явно задокументировать и, если возможно, проверить у платформы, какой заголовок и с каким числом «прыжков» она реально подставляет; ограничить размер тела запроса до `zod`-валидации.

**Конкретная приёмка следующего этапа.** Зафиксировать реальную границу доверия для каждого используемого ingress; произвольный XFF не считать доверенным. Лимит применять до JSON/Zod к фактически прочитанным байтам потока, а не только Content-Length. Проверки: поддельные XFF/real-IP, неизвестный клиент, отсутствие/заниженный/некорректный Content-Length, chunked-переполнение, многобайтный UTF-8, malformed JSON и обычные payload всех форм. Ответ на превышение — 413 без сохранения/отправки лида; существующие идемпотентность/лимиты/контракт ошибок не ломать. Неподтверждённую конфигурацию Amvera/Vercel не выдавать за проверенную; отделить кодовый результат от platform_verified.

### PT-022 · Ценовой якорь hero главной страницы соответствует заявленному продукту

**Статус:** ЧАСТИЧНО / ПЕРЕПРОВЕРИТЬ КОНТРАКТ. Hero переработан; автоматическая согласованность всех цен и продуктов не принята отдельно.

**Приоритет исходного плана:** P1. **Связь:** T8-003.

**Источники:** триангулировано `A‑15`(MD, `F-15`) + `B‑F106`, независимо подтверждено этим документом чтением `content/homepage.ts`: `h1: "Теневые и парящие потолки под ключ..."`, а `subtitle: "От 1 000 ₽/м² · ..."` — это цена **простого** потолка (`pricing.ceiling.standard`), а не теневого/парящего, которые начинаются от `800 ₽/м²` за полотно плюс `950`/`2500 ₽/м.п.` за профиль. **Важное уточнение этого документа:** на страницах конкретных услуг (например, `/tenevoy-profil`) якорь уже реализован корректно через `servicePriceAnchor()` из `content/pricing.ts` — то есть паттерн правильного решения в проекте уже есть, задача — привести к нему главную страницу, а не изобретать новый.
**Решение.** Заменить подзаголовок hero на один из двух вариантов: (а) явно назвать, к какому продукту относится цифра («Простой потолок — от 1 000 ₽/м². Теневой и парящий считаются по площади и длине профиля в калькуляторе»), либо (б) показать составной якорь по каждому из заявленных в H1 продуктов, посчитанный из `content/pricing.ts`, а не захардкоженный отдельно.
**Приёмка.** Число в hero соответствует продукту, названному в H1, при любом изменении `content/pricing.ts` (нет расхождения между hero и сервисными страницами).

### PT-024 · Корректный payload аналитических событий подтверждения параметра

**Статус:** РЕАЛИЗОВАНО В КОДЕ, LOCAL_VERIFIED. `quiz_param_confirm` получает значение своего параметра в обеих ветках `goNext`.

**Источники:** `A‑14`(MD, `F-14`) · `T‑327`. `quiz_param_confirm` в `PriceCalculatorQuizV2.tsx` передаёт `room.area` вне зависимости от реального параметра (трек, карниз, количество светильников и т.п.). Ввести типизированную таблицу `param → value` с реальным значением для каждого типа параметра.

### PT-047 · Требования доступности для новых изображений (расширение `PT‑028`)

**Статус:** КОНТРАКТ СОБЛЮДЁН ДЛЯ ВНЕДРЁННЫХ КАРТИНОК (17.10.2026). Схемы и кадры, чей смысл уже выражен заголовком, идут с `alt=""`; у фото скрытой ниши alt описывает то, чего нет в названии варианта. `aria-pressed` остаётся на кнопке, заголовок видим и при активном состоянии с картинкой (e2e). Полный ascree-прогон остаётся за PT-028.

**Приоритет исходного плана:** P3. **Связь:** T8-025.

**Источники:** `IMG‑08` (документ 2) · `01-audit-idei.md`, риск 4.
**Проблема.** Нужно явно зафиксировать контракт, чтобы будущий `@axe-core/playwright`-прогон из `PT‑028` не начал падать из-за новых изображений.
**Решение.** Правило: если `imageAlt` по смыслу дублирует уже видимый `title` карточки — `alt=""` и `aria-hidden="true"` на самой картинке (декоративное дополнение, весь смысл несёт текст); если картинка добавляет информацию, которой нет в `title`/`meta` — `alt` обязателен и лаконичен. Ни для одного экрана изображение не может быть единственным способом отличить активный вариант от неактивного (это уже обеспечено активным состоянием текста/фона `OptionCard`, но нужно явно проверить после интеграции, что рамка/заливка активного состояния не была случайно перекрыта картинкой).
**Приёмка.** Ручной проход Tab/Shift+Tab по всем изменённым экранам — фокус и объявления скринридера не изменились по сравнению с текущим состоянием; включить эти экраны в объём будущего прогона `PT‑028`, когда он будет выполняться.

### PT-048 · Флаг фичи, поэтапный вывод и измерение по существующим событиям аналитики

**Статус:** ОТКРЫТО. Флаг NEXT_PUBLIC_QUIZ_STEP_IMAGES не найден в коде квиза; baseline не получен.

**Приоритет исходного плана:** P3. **Связь:** T8-036, T8-027.

**Источники:** `01-audit-idei.md`, риск 6 · правило 8 раздела 2 ТЗ v5 · паттерн `PT‑035`.
**Проблема.** Это P3-гипотеза без baseline; правило раздела «P3» ТЗ v5 требует baseline и возможность отката, а не «просто релиз кода».
**Решение.** (1) Ввести `NEXT_PUBLIC_QUIZ_STEP_IMAGES` (дефолт `false`), по аналогии с `NEXT_PUBLIC_CALC_QUIZ_V2`. (2) До включения флага кому-либо — снять baseline по существующим `trackQuizScreenView`/`trackQuizBack`/`trackQuizParamConfirm` (`lib/analytics.ts`) за 2–4 недели: долю ушедших на каждом `param`-экране (в первую очередь `ceiling`, `cornice`, `track` — самые жаргонные). (3) Включать флаг сначала только для этих трёх экранов (`PT‑039`, `PT‑040`, `PT‑041`), не для всех девяти сразу — так сравнение будет чище. (4) Через 2–4 недели после включения — повторно снять те же метрики и сравнить; если завершаемость `param`-экранов не выросла или упала — откат публичным флагом с новой сборкой preview/релиза, задача переводится в статус «гипотеза не подтвердилась», не удаляется код, а документируется вывод.
**Приёмка.** Флаг существует и по умолчанию выключен; отчёт по задаче обязан содержать baseline-числа **до** и **после**, а не только факт «код выкатили» (по правилу 9 раздела 2 ТЗ v5). Если у исполняющего агента нет доступа к Яндекс.Метрике для снятия чисел — прямо написать «доступ отсутствует» и передать владельцу пошаговую инструкцию, что смотреть в каком отчёте Метрики.

**Поправка к main.** NEXT_PUBLIC_* в Next.js фиксируется при сборке: обещание отката runtime-переменной «без деплоя» неверно. Проверять отдельные build on/off либо отдельно реализовать и принять runtime-конфиг. Включение production-флага также требует разрешения владельца.

### PT-049 · Правило добросовестности изображений — закрепить письменно, не полагаться на общую формулировку правила 5

**Статус:** ПРАВИЛО СОБЛЮДЕНО ДЛЯ НОВЫХ АССЕТОВ (17.10.2026). AI-генерация не использовалась вовсе: фото — только реальные кадры компании (производные `proj-*` с сохранённой атрибуцией), остальное — векторные схемы, ни одна из них не мимикрирует под фотографию, и при их выборе видна подпись «Разрез схематичный». Требование «фотореалистичный рендер с подписью» не понадобилось.

**Приоритет исходного плана:** P3. **Связь:** T8-024; B8-004.

**Источники:** `01-audit-idei.md`, риск 1.
**Проблема.** Общее правило 5 раздела 2 ТЗ v5 говорит про текстовые факты (отзывы, реквизиты, гарантии); для изображений нужен явный, буквальный аналог, иначе разные исполнители будут трактовать «можно ли сгенерировать фотореалистичное фото объекта» по-разному.
**Решение.** Зафиксировать в актуальном брендбуке/дизайн-системе из B8-002/005 (там же, где по `PT‑027` фиксируются роли цветов) правило: «Любое изображение в интерфейсе, похожее на фотографию конкретного результата работ, обязано быть либо настоящей фотографией реального объекта компании (с фактическим alt), либо визуально однозначно опознаваемо как схема/иллюстрация (не фотореалистичный рендер, выданный за объект). Фотореалистичные AI-иллюстрации допустимы только для абстрактных, не привязанных к конкретному материалу концепций и обязаны иметь подпись «иллюстрация», видимую без наведения/клика.»
**Приёмка.** Правило добавлено в актуальном брендбуке/дизайн-системе из B8-002/005; все изображения, добавленные в `PT‑039…PT‑043`, вручную сверены с этим правилом и художественным брифом раздела 4 перед мёржем.

## 4. Бриф и зависимости иллюстраций (вместо ссылок на удалённый «документ 4»)

- Приоритет: подтверждённое реальное фото → наглядная схема → явно маркированная AI-концепция. Никаких вымышленных объектов компании. Все изображения — высочайшего визуального качества, но в рамках бюджета PT-046.
- Карниз built-in/surface и трек built-in/surface: одинаковый ракурс/масштаб сечения, простая геометрия и ясно различимый способ монтажа; не утверждать неподтверждённую совместимость конкретной системы. Обобщённое фото трека не доказывает монтажный подтип.
- В одной смысловой группе покрыть все значимые положительные варианты; иначе оставить группу текстовой. none/отрицательный вариант — явное исключение PT-040…042, а не повод иллюстрировать только самый дорогой положительный вариант.
- Продвинутый сценарий: концептуальная иллюстрация с постоянно видимой подписью, без обещания реально доступного SMART-комплекта. Текст и цена остаются видимыми при ошибке загрузки.
- Пиктограммы помещений и переключателей — SVG/currentColor, один стиль и вес линии, не растровая генерация под 20 px.
- Порядок: PT-038 → PT-046/049 → PT-039…042 → PT-043…045 → PT-047. Флаг PT-048 закладывать до первого включения иллюстраций; сначала off, затем сборки on/off, baseline, ограниченный согласованный эксперимент. FSM и тарифы в этом блоке не менять.
