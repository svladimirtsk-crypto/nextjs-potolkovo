**Дата:** 22.10.2026. **Ветка:** `feat/company-rebrand-v7-preview`. Основа работы: опубликованный `6ca4618` (Vercel **success** для него); перечисленное ниже проверено **локально после** этого SHA, без PR/merge/main/production и без подтверждения поставщика. Статус обоих сценариев — **частично**, не инженерная/коммерческая приёмка.

## Контракт и реализация

1. **LED‑19 · московское наблюдение.** Нормализатор, live feed, staged refresh, компактный индекс и UI принимают только явный числовой `stockByWarehouse.moscow`/«Остатки Мск». Отсутствие или некорректность не превращаются в 0 или `available=true`; противоречивые московские наблюдения отклоняются до записи. Другие склады не используются. Время наблюдения берётся только из даты источника с часовым поясом, не из времени сборки; при отсутствии корректной даты — `null`. `reported_zero` и `supplier_unavailable` исключаются из автоматического LED-подбора БП/контроллера и стартового выбора ленты; заданная вручную лента с нулём требует проверки. Готовые серверные комплекты не используют такой товар. `unknown` остаётся предварительным кандидатом, **не** обещанием наличия. Положительное число — тоже не резерв. Карточки, FAQ и лид не называют это «в наличии».
2. **LED‑20 · версия и diff.** Версия `cat-sha256-…` вычисляется по содержимому feed (не доверяется заявленной версии). Изолированный feed-refresh пишет полный review price/vendorCode/offerId/unit/priceUnit/packQty/московский остаток/available и только после проверки публикует кандидат в рабочие файлы. Чистая функция сравнивает сохранённый draft по исходному `productId`, показывает клиенту изменение цены, артикула, единицы, упаковки, московского остатка **до** применения. Требуется отдельное подтверждение; единица/упаковка или отсутствующий productId блокируют автоматический перенос. Исторический draft остаётся доступен для явного выбора «начать заново», не стирается при открытии сверки.
3. **Сквозной след.** Готовые комплекты тоже получают catalogVersion и исходные параметры. Компактный лид сохраняет версию, заявленное клиентом подтверждение, упаковку и складскую метку; Zod ограничивает поля. Сервер заново берёт цены/московский остаток/время наблюдения из своего каталога, отдельно фиксирует его версию и расхождение с клиентской, не заменяет исчезнувший `productId` по совпавшему артикулу. Менеджеру передаются предупреждения о расхождении версии/цены и о неподтверждённом/нулевом московском остатке. `priceCheck.status=verified` означает **только совпадение арифметики**, а не подтверждение товара, цены счёта или резерва. Клиентские версии/acceptedAt — запись заявления браузера, не независимое доказательство согласия.

**Источники:** исходный `data/eks-feed2-snapshot.json` не менялся; архивный XML в `docs/evidence/catalog-led-audit/raw/sources/` — историческая проба, а не актуальный ответ EKS. Производный индекс — **545 позиций, 113 847 Б (~111,2 КиБ), 0 известных московских остатков**: последнее означает unknown, не «у всех ноль». `catalogVersion=cat-sha256-d36ba50dbef6eca9d50785292ac6e07f0b54e8a1ab5302f4a90e9e13cd82443f`. Новые складские значения и цена/упаковка поставщика не выдумывались. Данные иных складов в тестах — *синтетические отрицательные фикстуры*, не коммерческая информация.
