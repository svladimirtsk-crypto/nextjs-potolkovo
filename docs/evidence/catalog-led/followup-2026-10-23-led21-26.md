## Решение владельца и деньги · LED‑21

- Владелец 23.10 подтвердил: LED-лента, питание и управление **в целом оплачиваются отдельно** от потолочных ставок парящего контура, световой линии и карниза; состав монтажа LED **не утверждён**. Проценты действующих скидок не менялись.
- Исключение: в действующей `corniceLighting.psu` уже заложена **материальная стоимость БП 1 500 ₽/шт**. Только явное назначение выбранного **штучного LED-БП** конкретной действующей задаче карниза заменяет эту включённую часть. Снять 1 500 ₽ за назначенную штуку с **сырой** потолочной суммы, заново применить минимальный заказ, прибавить полную цену выбранного SKU отдельной позицией блока света. Не считать «цену только сверх 1 500 ₽» и не вычитать без связи.
- `lib/lighting/led-commercial.ts` отклоняет ложную/дублированную/избыточную привязку целиком и БП с известным нулём Москвы или пометкой недоступности; неподвязанный БП оставляет в заявке явный вопрос о риске двойного начисления. Цена и факт резерва до согласования EKS остаются неподтверждёнными.
- Клиентский и независимо пересчитанный серверный `totals` сохраняют отдельно `ledIncludedRub` (заменяемая часть ставки), `ledEquipmentExtraRub` (регулярная стоимость выбранного LED-оборудования **до существующей скидки**) и `ledCeilingDeltaRub` (фактическая дельта потолка **после** повторного применения минимума). При срабатывании минимального заказа последняя может быть меньше 1 500 ₽ по модулю или 0. `ledPsuReplacementRub` остаётся для прежнего контракта. Эти поля предварительные и не являются счётом.

## Контекст, BOM, версия и отправка · LED‑22–24

- Выбор метража/рядов/зон/SKU ленты сохраняется как **неподтверждённый** `ledPlanning`, привязанный к задаче комнаты, если она есть; пустая корзина не получает выдуманный BOM. Изменение плана или корзины меняет `quoteVersion` и предварительный подбор, но не заменяет вручную выбранные БП/контроллеры: интерфейс просит сверить старую корзину.
- `ledReview.status=needs_review` проходит через корзину → snapshot → Zod → серверную сверку → письмо: задачи, план, выбранные SKU/количества/роли, назначения, версии правил/каталога/quote и все вопросы инженеру. Исторические записи лида не ломаются (новые поля сумм необязательны для старого формата). Сервер не доверяет клиентскому вычету, BOM-версии и `priceCheck.status=verified` как доказательству склада/электрики.
- В браузере desktop/mobile проверено: отказ от диалога сохраняет LED-черновик без POST; ошибка 500 и ручной retry сохраняют `requestId`, план, BOM и `quoteVersion`. Общие регрессии consent/outbox/rescue остаются в полном наборе. **Не реализован** ранее отложенный standalone cart reload; другой deploy не обновит автоматически уже открытую вкладку.

## Каталог · LED‑26

- `scripts/refresh-feed.mjs` по-прежнему принимает нормализованный JSON (реальный XML-импорт — отдельная очередь), сохраняет diff для ручного PR-review и сначала запускает проверки SKU, индекса и всех обложек в изолированной директории. Пропавшая обложка теперь **блокирует** локальное переключение вместо молчаливого ухудшения покрытия.
- `scripts/catalog-release.mjs` создаёт неизменяемые выпуски `data/catalog-releases/<releaseId>/` с манифестом SHA‑256 для каждого JSON/отчёта и каждого используемого локального фото. На первом **контролируемом** refresh плоский last-known-good становится базовой версией; существующие `data/*.json` становятся ссылками через `data/catalog-current`. После полной проверки **один атомарный rename симлинка** выбирает новый выпуск. Изменённые фото получают новые `/catalog/releases/<releaseId>/…` URL; старые файлы не переписываются. До переключения проверяются ожидаемые старая версия/указатель и эксклюзивный lock.
- `node scripts/refresh-feed.mjs --check` ничего не публикует; `--dry-run` показывает diff без записи. `--rollback` без `FEED_URL` возвращает предыдущую проверенную версию одним переключением указателя; `--rollback=<releaseId>` требует корректный ID и целостный выпуск. Сбой до switch сохраняет старый указатель, ошибка после switch переключает обратно; уже опубликованный кратковременно выпуск не удаляется, если читатель успел его закрепить. `build-catalog-index`, `build-catalog-images` и ручной скрипт обложек не переписывают активный неизменяемый выпуск.
- **Граница атомарности:** это источник данных для последующей проверяемой Git-сборки/PR, **не горячая транзакция для произвольных одновременных многофайловых чтений**. Такой читатель должен закрепить один release ID на время операции; одновременно открытая старая вкладка сама не мигрирует. GitHub workflow создаёт PR, а не merge/deploy; перед созданием PR теперь также запускает off production build и bundle gate на выпущенных файлах. CI-путь ещё не сработал для реального выпуска. Реальный новый EKS-feed и первое переключение рабочего дерева намеренно **не выполнялись**. Доступ к production и основной ветке не менялся.
