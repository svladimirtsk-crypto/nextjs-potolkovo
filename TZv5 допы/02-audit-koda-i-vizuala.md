# Аудит кода и визуала: готовность калькулятора к добавлению изображений

**Метод:** построчное чтение исходников ветки `quizv2ver1` (не пересказ прежних аудитов). Ниже — только то, что подтверждено конкретным файлом/строками. Находки пронумерованы `IMG‑01…IMG‑12`, чтобы не путать с реестром `PT‑xxx`/`A‑xx`/`T‑xxx` из предыдущих документов; в дополнении к ТЗ (документ 3) каждая находка превращена в задачу `PT‑0xx`.

## 1. Карта воронки Шага 0 (квиз параметров)

Источник: `lib/step0-fsm.ts` (`ALL_PARAMS`, `getEnabledParams`, `getNextScreen`) + экраны в `components/calculator-modal/step0/quiz-v2/screens/`.

Линейная последовательность экранов (часть — условная, зависит от сценария):

```
scenario → roomPicker → [param: area] → [param: ceiling] →
  (если shadow/floating включены) → [param: shadowProfile | floatingProfile] →
  (если "современный" сценарий) → [param: lightLines] →
  [param: cornice] →
  (если "современный" сценарий) → [param: track] →
  [param: chandeliers] → [param: lights] →
  (следующая комната, если есть) → summary
```

Далее пользователь попадает в **Шаг 1** — подбор реального освещения (`wizard-step1-lighting.tsx`) — и в **Шаг 2** — сводка/лид (`wizard-step2-summary.tsx`).

## 2. Находка IMG‑01 — `OptionCard` не имеет слота для изображения вообще

Файл: `components/calculator-modal/step0/quiz-v2/ui.tsx`, функция `OptionCard` (строки 26–36). Компонент принимает только `{ active, title, meta, onClick }` и рендерит `<button>` с двумя строками текста. У него нет пропа под иконку/картинку в принципе — это не «картинки временно скрыты», а архитектурное отсутствие такой возможности.

Этот же `OptionCard` используется **без единого исключения** на всех экранах с выбором варианта:
- `ScenarioScreen.tsx` — сценарий (Стандартный/Современный/Продвинутый) — свой инлайн-рендер кнопок, тоже 100% текст (не переиспользует даже `OptionCard`, дублирует разметку — отдельный минус для консистентности, см. `IMG‑09`).
- `ParamScreen.tsx` — площадь (режим «комната»/«вся квартира»), тип потолка (простой/теневой/парящий), карниз (4 варианта), участок профиля (весь периметр/частично), световые линии (вкл/выкл), трек (3 варианта), люстры (вкл/выкл), точечные светильники (вкл/выкл) — **все** через `OptionCard`.
- `RoomPickerScreen.tsx` — 9 типов помещений (Кухня/Гостиная/Спальня/Детская/Кабинет/Санузел/Коридор/Прихожая/Другое) — отдельные `<button>`, тоже только текст, без иконок.

Итого: **все развилки квиза без исключения текстовые.** Это самый прямой и однозначный код-факт, лежащий в основе всей идеи.

## 3. Находка IMG‑02 — асимметрия с Шагом 1: рядом уже есть полноценный фото-стек

Файл: `wizard-step1-lighting.tsx` (1395 строк). Здесь уже есть:
- превью товара из фида (`CatalogBrowse`, `ProductImage.tsx`/`ProductImageLightbox.tsx`);
- состояние увеличенного просмотра (`zoomImage`, строки 629–630), клавиша `Escape` для закрытия (строка 705), сам компонент `ImageQuickPreview` (строка 1118).

То есть инфраструктура «показать лиду картинку и дать её увеличить» в проекте **уже существует и обкатана**, просто на один шаг позже, чем нужнее всего (см. документ 1, риск/аргумент №3). Практическое следствие: часть UI-паттернов (обёртка над `<img>`, лайтбокс) можно частично переиспользовать по аналогии, а не изобретать с нуля — но для квиза не нужен полноценный лайтбокс с зумом, только компактная превью-карточка (иначе это тот же риск IMG‑07 из документа 1 про перегрузку экрана).

## 4. Находка IMG‑03 — пайплайн изображений уже зрелый и полностью пригоден для повторного использования

Три файла образуют готовую систему:
- `scripts/build-images.mjs` — на сборке генерирует AVIF/WebP в 480/960/1440 из `public/*.jpeg` в `public/optimized/`, считает blur-плейсхолдер (base64), пишет всё в `data/image-manifest.json`; идемпотентно (пересобирает только изменившееся); уже содержит адаптивный подбор качества под весовой бюджет (`WEBP_QUALITY_STEPS`, `AVIF_QUALITY_STEPS`) и сам бюджет (`BUDGETS_KB`: hero ≤150 КБ, `proj-*` ≤80 КБ).
- `data/image-manifest.json` — манифест «путь → {width, height, widths[], blurDataURL}», уже содержит записи для всех текущих `public/*.jpeg`.
- `components/ui/picture.tsx` — React-компонент `<Picture>`, читает манифест, отдаёт `<picture>` с `source[avif]`/`source[webp]` и `srcSet`, ставит `width`/`height` (защита от CLS), `loading="lazy"` по умолчанию, `fetchPriority`/`priority` для LCP-картинок, **graceful fallback** на исходный `<img src>`, если записи в манифесте нет (не ломает страницу, если картинку забыли пересобрать).

`next.config.ts` держит `images: { unoptimized: true }` (хостинг Amvera без runtime-оптимизатора), поэтому корректный путь для новых картинок — только через этот пайплайн (`next/image` тут не даст оптимизации).

**Вывод:** для реализации идеи не нужна новая инфраструктура — нужно (а) добавить исходники в `public/`, (б) прогнать `npm run build:images`, (в) прокинуть проп `imageSrc`/`icon` в `OptionCard` и рендерить `<Picture>` внутри. Инженерный риск — низкий.

## 6. Находка IMG‑05 — реальные пробелы: где фото объективно не хватает

1. **Карниз — «Встроенный карниз» и «Накладной карниз».** В `content/homepage.ts` `cornices` — 4 варианта (`none`, `built-in`, `hidden-niche`, `surface`). Настоящее фото есть только для `hidden-niche` (проект `proj-cornice-*`). Для `built-in` и `surface` — только один общий `svc-cornice.jpeg`, который использован на странице услуги «карниз» целиком, а не отдельно для этих двух подтипов. Использовать одно и то же фото для двух разных вариантов — хуже, чем не использовать вообще (см. документ 1, риск 5).
2. **Трек — «Встроенный трек» и «Накладной трек».** Аналогично, `svc-track.jpeg`/`svc-tracksale.jpeg` не разделены по монтажному типу (`built-in` vs `surface`).
3. **Сценарий «Продвинутый» (SMART-свет и сценарии управления).** Текст `ScenarioScreen.tsx`: «SMART-свет и сценарии управления — обсудим лично» — концепция (управление со смартфона/сценарии освещения), для которой в архиве вообще нет подходящего кадра (существующие фото — статичные интерьеры, не про smart-управление).
4. **9 типов помещений (`RoomPickerScreen.tsx`)** — ни одной иконки/фото не предусмотрено и, по сути, фото тут избыточны (см. §8).
5. **Режим расчёта «Одну комнату» / «Всю квартиру или дом»** (`ParamScreen.tsx`, блок `AREA`) — два `OptionCard` без какой-либо визуальной опоры.
6. **Вкл/выкл-переключатели** («Без подсветки»/«Добавить подсветку» для карниза, «Без люстр»/«Добавить установку», «Без светильников»/«Добавить светильники») — концептуально это скорее пиктограммы-«переключатели», чем фото.

## 7. Находка IMG‑06 — устаревшая часть находки `PT‑017` требует переверификации

`data/catalog-images-missing.json` на момент аудита (чтение файла в ветке `quizv2ver1`) — **пустой массив** (`[]`). Задача `PT‑017` в ТЗ v5 утверждает «34 SKU без локального фото подтверждены» — на текущем `HEAD` ветки это не подтверждается: либо проблема уже устранена, либо файл не актуализируется отдельным скриптом на постоянной основе. Согласно правилу 10 раздела 2 ТЗ v5 («если у агента нет доступа/данные не проверены — написать явно»), это надо переверить командой `npm run check:catalog-images` перед тем, как опираться на цифру «34» в новых задачах, а не переносить её по инерции.

## 8. Находка IMG‑07 — ограничения вёрстки, которые определяют формат изображений

`components/calculator-modal/calculator-modal.tsx`:
- Мобильная модалка: `h-[100dvh] max-h-[100dvh] ... flex-col overflow-hidden` (строка ~420) — вся модалка = высота экрана, без внешнего скролла страницы.
- Внутри — фиксированный хедер с заголовком и прогресс-баром (`StepNav`), под ним на мобильном — sticky `PriceStrip` (`currentStep !== 2`, `lg:hidden`), и только затем прокручиваемая зона `calculator-modal-content` (`flex-1 overflow-y-auto`, строка ~464).
- Кнопки навигации («Назад»/«Далее»/«Подтвердить») в текущем прочтении рендерятся вне этого куска (нижний футер, вне `contentRef`), то есть они не «утекают» вниз бесконечно — но и не сокращают доступную высоту контента произвольно.

Практический вывод: у типового iPhone SE (375×667 px) высота видимой прокручиваемой зоны — плюс-минус 420–480 px после вычета хедера/`PriceStrip`/футера. Один экран квиза (`SectionCard` + до 4 `OptionCard` в сетке 2×2 + `RangeField`) уже сегодня иногда требует прокрутки. Добавление изображений **обязано** укладываться в сетку `grid gap-3 sm:grid-cols-2`, не создавая отдельный полноширинный блок сверху — то есть миниатюра должна быть частью самой карточки `OptionCard`, а не новым элементом над ней.

## 9. Находка IMG‑08 — состояние доступности `OptionCard` сегодня (базовая точка для сравнения)

`OptionCard` уже сегодня: `aria-pressed={active}`, `min-h-11` (44 px, ориентир по `PT‑028`), явный текстовый контраст (`text-slate-950`/`text-white` в активном состоянии на `bg-slate-950`). Это хорошая базовая точка — новую картинку нужно добавлять, не понижая этот уровень (не убирать текст, не терять `aria-pressed`, не превращать кнопку в чистую картинку без названия).

## 10. Находка IMG‑09 — дублирование разметки карточек-опций (сам по себе визуальный техдолг)

`ScenarioScreen.tsx` не использует общий `OptionCard` из `ui.tsx`, а держит собственный инлайн-рендер кнопки с почти идентичной, но не идентичной версткой (`rounded-2xl` вместо разбираемого класса, свои условия активного состояния). Это значит, что при добавлении изображений в `OptionCard` понадобится **либо** привести `ScenarioScreen` к общему компоненту (полезный побочный рефакторинг, снижает будущую рассинхронизацию стилей), **либо** продублировать проп изображения и в локальную кнопку сценария — второе явно хуже и плодит долг дальше.

## 11. Находка IMG‑10 — бюджет веса не покрывает новый класс «миниатюра квиза»

`BUDGETS_KB` в `build-images.mjs` определяет пороги только для `hero*` и `proj-*`. Нового префикса под миниатюры квиза нет. Без явного добавления записи типа `{ test: (name) => name.startsWith("quiz-"), limitKb: 20, label: "квиз" }` новые файлы либо попадут под самый мягкий дефолт (если он есть) и раздуют вес, либо не будут проверяться вовсе.

## 12. Находка IMG‑11 — единственный акцентный цвет UI, задокументировать до, а не после добавления иллюстраций

Существующая, ещё не закрытая задача `PT‑027` («задокументировать роли цветов интерактивных элементов») впрямую влияет на новую работу: если иллюстрации будут содержать собственные яркие/произвольные цветовые акценты (типичная проблема сток-иллюстраций и части AI-генераций по умолчанию), они визуально «поспорят» с единственным принятым акцентом `bg-slate-950`. Рекомендуется закрыть/хотя бы зафиксировать `PT‑027` парой предложений в README до начала работы над иллюстрациями, чтобы у промптов (документ 4) была явная цветовая привязка.

## 13. Находка IMG‑12 — нет защитного теста на деградацию до текстового варианта

Сегодня `<Picture>` уже терпимо ведёт себя при отсутствии записи в манифесте (откат на `<img src>` напрямую). Но для нового пропа `imageSrc` в `OptionCard` такого явного контракта ещё нет — его нужно спроектировать сразу (если `imageSrc` не передан или путь отсутствует в манифесте, карточка обязана остаться полностью работоспособной чисто текстовой версией, без визуальных «дыр» типа сломанной иконки), и покрыть это тестом по аналогии с уже существующими `scripts/check-images.mjs`.

## 14. Общий визуальный вывод

Дизайн-система проекта дисциплинирована и минималистична: один основной акцент (`slate-950`), последовательная радиусная сетка (`rounded-2xl`/`rounded-[1.5rem]`), уже есть работающий пайплайн адаптивных изображений с бюджетами по весу и защитой от CLS. Это низкий архитектурный риск для добавления изображений — правки локализуются в `ui.tsx` (расширение `OptionCard`), экранах `ParamScreen.tsx`/`ScenarioScreen.tsx`/`RoomPickerScreen.tsx` и в `build-images.mjs`/`image-manifest.json`, без затрагивания `lib/calculator/*` (расчёт цены) и `app/api/lead/*` (приём заявки) — то есть без пересечения с P0/P1 задачами ТЗ v5, что соответствует правилу «не менять визуальный слой и ядро расчёта в одном PR» из раздела 6 ТЗ v5.

Главные технические условия успеха (детализированы в документе 3):
1. Расширить `OptionCard`, не создавая параллельный компонент.
2. Приоритет реальных фото из `content/home-assets.ts` там, где они точно соответствуют варианту.
3. Новые иллюстрации — только там, где реального фото объективно нет, с отдельным весовым бюджетом и явным стайлгайдом.
4. Явный откат к тексту при отсутствии картинки, флаг фичи, baseline по существующим событиям аналитики.
